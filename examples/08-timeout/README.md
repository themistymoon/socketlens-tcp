# 08 — Timeout, asserted as the expected outcome

## What this demonstrates

The mock is slower than the client's patience, so no response arrives. The test
**passes**, because a timeout is what the scenario asked for.

## Run it

```
npm run examples -- --only 8
```

## What you should see

```
scenario  timeout-is-expected           PASSED   (timeout, 504 ms)
```

Note the two numbers: the outcome is `timeout` and the duration is ~504 ms, not
2500 ms. The client stopped waiting at its own 500 ms deadline rather than sitting
there until the mock finally answered. The runner asserts `durationMs < 2000`, which
fails if the timeout does not actually fire.

## The configuration

| Value              | Setting                                   |
| ------------------ | ----------------------------------------- |
| `response.delayMs` | 2500 ms — the mock answers eventually     |
| `timeoutMs`        | 500 ms — the client gives up first        |
| `expect.timeout`   | `true` — a timeout is the passing outcome |

## Why "expected timeout" is a distinct concept

Without `expect.timeout`, this scenario would report outcome `timeout` and **fail**,
which is correct for the common case: you asked for a response, none came, something
is wrong.

But timeout behaviour is itself worth testing. "Does my client give up after 500 ms
rather than hanging forever?" is a real question, and answering it requires a peer
that does not respond. `expect.timeout: true` inverts the verdict so the absence of a
response becomes the success condition.

The assertion engine settles **arrival** before it settles content, in this order:

1. Did the exchange time out? If `expect.timeout` is set → **pass**, and stop.
2. Did the peer disconnect mid-message? If `expect.disconnect` is set → **pass**, stop.
3. Otherwise, is there a complete response? If not → outcome `timeout` or `failed`.
4. Only now compare status code, phrase, headers, and body.

Steps 1 and 2 must come first because steps 3 and 4 have nothing to work with when no
response exists. There is no status code to compare against when nothing arrived.

## Contradictory expectations are rejected

`expect.timeout` cannot be combined with `statusCode` or `disconnect`:

```json
{ "timeout": true, "statusCode": 200 } // rejected: 422 INVALID SCENARIO
```

That scenario is unsatisfiable — it demands both that no response arrive and that the
response have status 200. Rather than silently picking an interpretation, validation
rejects it before the test runs. The same applies to `disconnect` + `statusCode`, and
to `body` + `bodyContains`.

Catching this at validation time rather than at assertion time matters: an
unsatisfiable scenario that runs will always fail, and the engineer will spend their
time debugging the system under test instead of the scenario.

## What a timeout is not

A timeout is a **local** decision. Nothing is sent to the peer, no TCP reset is
generated by the timeout itself, and the peer is not informed. From the mock's
perspective its 2500 ms timer is still running; it will attempt to write to a socket
the client has abandoned.

This is also why a timeout tells you nothing about _why_ the peer was silent. The
request may never have arrived, or arrived and been ignored, or been processed with
the response still in flight. TCP's reliability guarantee covers delivery of bytes
that the peer's kernel acknowledged — it does not tell the application whether the
remote _application_ ever looked at them. Distinguishing those cases requires
application-level acknowledgement, which is one of the things SLTP's `Request-ID`
correlation provides.
