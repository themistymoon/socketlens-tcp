# บทสาธิต SocketLens TCP

**ระยะเวลา** ประมาณ 5 นาที
**รูปแบบ** สาธิตสดผ่านบรรทัดคำสั่ง ปิดท้ายด้วยส่วนติดต่อกราฟิก
**โครงร่างการนำเสนอทั้งหมด** อยู่ใน [presentation-outline-th.md](presentation-outline-th.md)

> **หมายเหตุสำคัญ** ผลลัพธ์ทุกบล็อกในเอกสารนี้คัดลอกมาจากการรันจริง ตัวเลขที่ท่านเห็นบนเวที

> แต่ **จำนวนส่วนย่อยและจำนวนข้อความที่ประกอบได้ต้องตรงกันเสมอ** เพราะนั่นคือประเด็นที่ต้องการสาธิต

## ขั้นตอนที่ 1 — PING และการดูไบต์จริง (45 วินาที)

**เทอร์มินัล B**

```bash
npm run cli -- ping --raw
```

**ผลลัพธ์จริงที่ได้**

```
[CLIENT +] 2026-08-04T10:13:15.564Z conn=conn-1 peer=127.0.0.1:7420
[CLIENT -> SERVER] 2026-08-04T10:13:15.567Z conn=conn-1 request=req-1 operation=PING bytes=36
[SERVER -> CLIENT] 2026-08-04T10:13:15.568Z conn=conn-1 request=req-1 status=200 phrase="OK" bytes=273
SLTP/1.0 200 OK  (273 bytes, 2 ms)
  Request-ID: req-1
  Server: SocketLens-TCP/0.1.0
  Timestamp: 2026-08-04T10:13:15.567Z
  Content-Type: application/json; charset=utf-8
  Content-Length: 100

Raw request bytes
  SLTP/1.0 PING\r\n
  Request-ID: req-1\r\n
  \r\n
```

**สิ่งที่ต้องชี้ให้ดู** (ชี้ด้วยเมาส์หรือเลเซอร์ทีละจุด)

1. หัวข้อ `[CLIENT -> SERVER]` และ `[SERVER -> CLIENT]` — ทั้งสองฝั่งพิมพ์ข้อความที่รับส่งจริง
2. บรรทัดเริ่มต้น `SLTP/1.0 PING` — นี่คือโปรโตคอลที่ผมออกแบบเอง ไม่ใช่ `GET / HTTP/1.1`
3. **`Request-ID: req-1` ปรากฏทั้งในคำขอและคำตอบ** — เป็นกลไกจับคู่ ทำให้ส่งหลายคำขอพร้อมกัน
   บนการเชื่อมต่อเดียวแล้วจับคู่คำตอบได้ถูกต้อง แม้เซิร์ฟเวอร์จะตอบไม่เรียงลำดับ
4. `\r\n` ปรากฏชัดเจนท้ายทุกบรรทัด และ `\r\n\r\n` คือตัวคั่นที่บอกว่าส่วนหัวจบแล้ว

**ประโยคเชื่อม** "ตอนนี้เห็นไบต์จริงแล้ว ต่อไปมาสร้างเซสชันเพื่อทดสอบกัน"

## ขั้นตอนที่ 2 — สร้างเซสชันและกฎจำลอง (45 วินาที)

```bash
npm run cli -- session create --name demo-th
```

**ผลลัพธ์จริงที่ได้**

```
[SERVER -> CLIENT] ... session=ses-3 status=201 phrase="SESSION CREATED" bytes=429
✔ Session ses-3 created (201 SESSION CREATED).
  id            : ses-3
  name          : demo-th
  state         : active
  mock endpoint : 127.0.0.1:4045
  rules         : 0
  results       : 0
Its mock endpoint listens on 127.0.0.1:4045; scenarios connect there over raw TCP.
```

**สิ่งที่ต้องชี้ให้ดู**

- `201 SESSION CREATED` — เป็นรหัสสถานะของ SLTP ที่ผมนิยามเอง
- **`mock endpoint : 127.0.0.1:4045`** ← จุดสำคัญ

**สิ่งที่ต้องพูด**

"ทุกเซสชันได้พอร์ต TCP จริงของตัวเอง ที่ระบบปฏิบัติการจัดสรรให้ ผมเลือกทำแบบนี้เพราะ
ถ้าจำลองการแบ่งข้อความในหน่วยความจำ มันจะเป็นแค่การแกล้งทำ แต่เมื่อเป็นซ็อกเก็ตจริง
การเรียก `write()` เจ็ดครั้งคือเจ็ดครั้งจริงบนสาย"

ต่อไปติดตั้งกฎจำลอง

```bash
npm run cli -- rule add --name pong --operation PING --status 200 \
  --body '{"message":"pong","note":"ตอบกลับ"}'
```

**ผลลัพธ์จริงที่ได้**

```
[SERVER -> CLIENT] ... status=212 phrase="RULE ADDED" bytes=522
✔ 212 RULE ADDED: rule "pong" installed.
  id              : rule-2
  name            : pong
  enabled         : true
  priority        : 0
  sequence        : 1
  match operation : PING
  response        : 200 OK
  response body   : {"message":"pong","note":"ตอบกลับ"}
```

**สิ่งที่ต้องชี้ให้ดู**

- `212 RULE ADDED` — SLTP มีรหัสเฉพาะสำหรับการเพิ่มกฎ ไม่ได้ใช้ 200 ทุกกรณี
- `priority: 0` และ `sequence: 1` — สองค่านี้กำหนดลำดับการประเมิน
  เรียงตาม priority จากมากไปน้อย เท่ากันจึงเรียงตาม sequence ลำดับจึงแน่นอนและทำซ้ำได้เสมอ
- **เนื้อความมีภาษาไทย** ซึ่งจะใช้เป็นตัวอย่างเรื่อง byte กับ character ในขั้นตอนถัดไป

**ถ้ามีเวลาเหลือ ให้เสริมประโยคนี้** "เนื้อความนี้มี 35 อักขระ แต่ยาว 49 ไบต์
เพราะอักษรไทยเจ็ดตัวใช้ตัวละ 3 ไบต์ `Content-Length` ของ SLTP นับเป็นไบต์เสมอ
ถ้าใช้ `str.length` ผู้รับจะอ่านขาดไป 14 ไบต์ แล้วสตรีมทั้งเส้นจะเสียหาย"

## ขั้นตอนที่ 3 — การแบ่งข้อความ ⭐ (75 วินาที)

> นี่คือจุดที่สำคัญที่สุดของการนำเสนอทั้งหมด ห้ามรีบและห้ามข้าม

```bash
npm run cli -- run examples/05-fragmented-message/bundle.json
```

**ผลลัพธ์จริงที่ได้**

```
PASSED  seven-fragments  res-7
  sent segments     : 7
  received segments : 1
  responses framed  : 1

TCP segments
  → +0ms  6 bytes   SLTP/1
  → +26ms 14 bytes  .0 PING\r\nReque
  → +52ms 18 bytes  st-ID: req-frag-1\r
  ...
  ← +...  240 bytes SLTP/1.0 200 OK\r\n...

PASSED  byte-at-a-time  res-8
  sent segments     : 134
  received segments : 1
  responses framed  : 1

2/2 scenario(s) passed
```

**สิ่งที่ต้องชี้ให้ดู — ทำตามลำดับนี้**

**ก่อนอื่น ชี้ที่ตัวเลขสามบรรทัดนี้**

```
sent segments     : 7      ← เขียนเจ็ดครั้ง
received segments : 1
responses framed  : 1      ← ปลายทางได้ข้อความเดียว
```

**สิ่งที่ต้องพูด**

"ข้อความเดียวยาว 134 ไบต์ ผมส่งด้วยการเรียก `write()` เจ็ดครั้ง และตำแหน่งที่ตัดผมเลือกให้ยากที่สุด
เท่าที่จะทำได้

ส่วนแรกได้แค่ `SLTP/1` — ตัดกลางโทเคนของเวอร์ชัน
ส่วนที่สองจบที่ `Reque` — ตัดกลางชื่อส่วนหัว
มีจุดหนึ่งที่ผมตัด **ระหว่าง CR กับ LF ของตัวคั่นบรรทัดเดียวกัน**
และอีกจุดผมตัด **หนึ่งไบต์ก่อนตัวคั่นส่วนหัวจะครบสี่ไบต์**

ทุกจุดเป็นตำแหน่งที่โค้ดที่เขียนแบบสมมติเอาเองจะพังทันที แต่ตัวถอดรหัสยังประกอบได้ถูกต้อง"

**จากนั้นชี้ที่สถานการณ์ที่สอง**

```
sent segments     : 134
responses framed  : 1
```

"สถานการณ์ที่สองส่งทีละหนึ่งไบต์ 134 ครั้ง — ทุกไบต์เป็นการเรียก `write()` แยกกัน
ผลลัพธ์ยังคงเป็นข้อความเดียวที่ถูกต้อง ตัวถอดรหัสไม่ตั้งสมมติฐานใด ๆ เกี่ยวกับขนาดของข้อมูลที่ได้รับ"

**ประโยคปิดขั้นตอนนี้** "นี่คือครึ่งแรกของสิ่งที่ต้องการพิสูจน์ — หนึ่งข้อความอาจมาถึงเป็นหลายชิ้น"

## ขั้นตอนที่ 4 — การรวมข้อความ ⭐ (45 วินาที)

```bash
npm run cli -- run examples/06-coalesced-messages/bundle.json
```

**ผลลัพธ์จริงที่ได้**

```
PASSED  two-messages-one-write  res-9
  sent segments     : 1
  received segments : 1
  responses framed  : 2
```

**สิ่งที่ต้องชี้ให้ดู**

```
sent segments    : 1      ← เขียนครั้งเดียว
responses framed : 2      ← ได้สองคำตอบ
```

**สิ่งที่ต้องพูด**

"ขั้นตอนที่แล้วคือหนึ่งข้อความมาถึงเป็นเจ็ดชิ้น ขั้นตอนนี้ตรงกันข้าม

ผมเรียก `write()` ครั้งเดียว แต่ในนั้นมีข้อความ SLTP สองข้อความติดกัน และปลายทางแยกออกได้ถูกต้อง
ตอบกลับมาสองคำตอบ

การแยกนี้อาศัย `Content-Length` ล้วน ๆ ตัวถอดรหัสอ่านความยาวของข้อความแรก ตัดไบต์ตามจำนวนนั้น
แล้ววนกลับไปตรวจว่าในบัฟเฟอร์ยังมีข้อความถัดไปอยู่หรือไม่

ถ้าลืมวนกลับ ข้อความที่สองจะค้างในบัฟเฟอร์และไม่มีวันถูกประมวลผล เพราะเหตุการณ์ `data`
ที่จะมากระตุ้นอาจไม่มีอีกแล้ว นี่คือบั๊กที่หาเจอยากมากในระบบจริง

และถ้าเขียนโค้ดแบบสไลด์ที่สองที่ผมแสดงตอนต้น ข้อความที่สองจะหายไปเงียบ ๆ โดยไม่มีข้อผิดพลาดใด ๆ"

## ขั้นตอนที่ 5 — ผ่าน ไม่ผ่าน หมดเวลา และผิดรูปแบบ (60 วินาที)

### 5.1 การทดสอบที่ผ่าน

```bash
npm run cli -- run examples/03-passing-test/bundle.json
```

ชี้ให้ดู `210 TEST PASSED` และรายการข้อที่ตรวจสอบซึ่งผ่านทุกข้อ

### 5.2 การทดสอบที่ไม่ผ่าน

```bash
npm run cli -- run examples/04-failing-test/bundle.json
```

ชี้ให้ดู `211 TEST FAILED` และรายการข้อที่ไม่ตรง **2 ข้อ**

**สิ่งที่ต้องพูด — เตรียมไว้ตอบคำถามล่วงหน้า**

"สังเกตว่า 211 อยู่ในกลุ่ม 2xx ซึ่งเป็นกลุ่มสำเร็จ ผมออกแบบไว้อย่างนี้โดยตั้งใจ

รหัสสถานะของ SLTP อธิบายผลของคำขอ SLTP ไม่ได้อธิบายผลของการทดสอบ
เซิร์ฟเวอร์รับคำขอ รันสถานการณ์ได้ เก็บผลได้ และตอบกลับครบถ้วน — คำขอนั้นสำเร็จโดยสมบูรณ์
การที่ผลไม่ตรงเป้าเป็นเนื้อหาของคำตอบ ไม่ใช่ความล้มเหลวของโปรโตคอล

ถ้าสถานการณ์เขียนผิดจนรันไม่ได้เลย นั่นจะเป็น 422 INVALID SCENARIO ซึ่งอยู่ในกลุ่ม 4xx อย่างถูกต้อง"

### 5.3 การหมดเวลา

```bash
npm run cli -- run examples/08-timeout/bundle.json
```

ชี้ให้ดูว่ากฎหน่วง 2500 ms ขณะที่สถานการณ์กำหนด timeout ไว้ 500 ms
สถานการณ์นี้ระบุ `expect: { timeout: true }` จึงถือว่าผ่าน เพราะการหมดเวลาคือสิ่งที่ตั้งใจทดสอบ

### 5.4 Content-Length ที่ผิดรูปแบบ

```bash
npm run cli -- run examples/09-malformed-content-length/bundle.json
```

**สิ่งที่ต้องชี้ให้ดู**

- `Content-Length: abc` → `400 BAD REQUEST` พร้อม `Reason: invalid-content-length`
- `Content-Length: -1` → `400 BAD REQUEST` พร้อม `Reason: negative-content-length`
- ทุกกรณีมีส่วนหัว **`Connection: close`**
- **สถานการณ์ถัดไปในไฟล์เดียวกันยังรันต่อได้** แสดงว่าเซิร์ฟเวอร์ไม่ได้ล้ม

**สิ่งที่ต้องพูด**

"เมื่อ `Content-Length` ใช้การไม่ได้ ผมไม่รู้ว่าเนื้อความจบตรงไหน จึงไม่รู้ว่าข้อความถัดไปเริ่มตรงไหน
ถ้าเดาแล้วเดาผิด ไบต์ของเนื้อความจะถูกอ่านเป็นบรรทัดเริ่มต้นใหม่ เกิดข้อผิดพลาดต่อเนื่องไม่จบสิ้น
สภาวะนี้เรียกว่า decoder poisoning

การปิดการเชื่อมต่อจึงเป็นทางเลือกเดียวที่ตรงไปตรงมา แต่สังเกตว่าปิดเฉพาะการเชื่อมต่อนั้น
เซิร์ฟเวอร์ยังให้บริการรายอื่นตามปกติ — ทุกการเชื่อมต่อมีบัฟเฟอร์และตัวถอดรหัสเป็นของตัวเอง"

## ขั้นตอนที่ 6 — ส่วนติดต่อกราฟิก (30 วินาที)

```bash
npm run dev
```

เปิดเบราว์เซอร์ตามที่อยู่ที่แสดง

**สิ่งที่ต้องชี้ให้ดู — ชี้เร็ว ๆ ไม่ต้องลงรายละเอียด**

| ตำแหน่ง     | เนื้อหา                                                          |
| ----------- | ---------------------------------------------------------------- |
| แผงซ้าย     | เซสชันพร้อมพอร์ตของปลายทางจำลอง และกฎเรียงตามลำดับการประเมินจริง |
| แผงกลางบน   | ตัวแก้ไขสถานการณ์ พร้อมช่องกำหนดขนาดส่วนย่อยและโหมดการส่ง        |
| แผงกลางล่าง | ไทม์ไลน์ข้อความ                                                  |
| แผงขวา      | ตัวตรวจสอบข้อความที่เลือก แสดงทั้งไบต์ดิบและส่วนที่แจงแล้ว       |

**สิ่งที่ต้องพูด**

"หนึ่งบรรทัดในไทม์ไลน์คือหนึ่งข้อความ SLTP ที่ประกอบสำเร็จ ไม่ใช่หนึ่งแพ็กเก็ต และไม่ใช่หนึ่งการเขียน
ความแตกต่างนี้คือประเด็นทั้งหมดของงาน

และหน้าเว็บนี้ไม่ได้เปิดซ็อกเก็ต TCP เอง เพราะเบราว์เซอร์ทำไม่ได้ มีกระบวนการตัวเชื่อมบนเครื่อง
ถือซ็อกเก็ตแทน ส่วน CLI ที่ใช้สาธิตมาทั้งหมดเชื่อมต่อ TCP โดยตรงไม่ผ่านตัวเชื่อมเลย"

## ประโยคปิดการสาธิต

"สรุปสิ่งที่เห็นวันนี้

ข้อความเดียวส่งด้วยการเขียนเจ็ดครั้ง — ปลายทางได้ข้อความเดียว
ข้อความเดียวส่งทีละหนึ่งไบต์ 134 ครั้ง — ปลายทางยังได้ข้อความเดียว
สองข้อความส่งด้วยการเขียนครั้งเดียว — ปลายทางได้สองข้อความ

สามกรณีนี้พิสูจน์ประโยคเดียวกัน คือ **TCP เป็นสตรีมไบต์ที่เชื่อถือได้และรักษาลำดับ
แต่ไม่รักษาขอบเขตของข้อความระดับแอปพลิเคชัน** และตัวถอดรหัสที่ถูกต้องต้องรับมือได้ทุกกรณี"

## การจัดการเวลาเมื่อเหลือน้อย

| เวลาที่เหลือ | ให้ตัดอะไร                            |
| ------------ | ------------------------------------- |
| เหลือ 4 นาที | ตัดขั้นตอนที่ 6 (ส่วนติดต่อกราฟิก)    |
| เหลือ 3 นาที | ตัดขั้นตอนที่ 5.3 และ 5.4 ด้วย        |
| เหลือ 2 นาที | เหลือเฉพาะขั้นตอนที่ 3 และ 4 เท่านั้น |

**ห้ามตัดขั้นตอนที่ 3 และ 4 เป็นอันขาด** สองขั้นตอนนี้คือเหตุผลที่โครงงานนี้มีอยู่

## เมื่อเกิดปัญหาระหว่างสาธิต

| อาการ                   | วิธีแก้ทันที                                                                      |
| ----------------------- | --------------------------------------------------------------------------------- |
| พอร์ต 7420 ถูกใช้อยู่   | `npm run start:server -- --port 7421` แล้วเพิ่ม `-p 7421` ในคำสั่งไคลเอนต์        |
| ไคลเอนต์ต่อไม่ได้       | ตรวจว่าเทอร์มินัล A ยังทำงานอยู่                                                  |
| ตัวอย่างรันแล้วไม่ผ่าน  | `npm run build:ts` ก่อน แล้วรันใหม่                                               |
| การสาธิตล้มเหลวสิ้นเชิง | เปลี่ยนไปใช้ภาพหน้าจอสำรอง พร้อมกล่าวว่าผลนี้ตรวจสอบซ้ำได้ด้วย `npm run examples` |
