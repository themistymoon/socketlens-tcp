## ขั้นตอนที่ 1 — PING และการดูไบต์จริง (25 วินาที)

> **พิสูจน์อะไร** ไวยากรณ์คำขอ-คำตอบของ SLTP (FR-2) และความหมายของรหัสสถานะ
> พร้อมแสดง `Request-ID` ที่ใช้จับคู่คำขอกับคำตอบ

**เทอร์มินัล B**

```bash
npm run cli -- ping --raw
```

**ผลลัพธ์จริงที่ได้**

```
[CLIENT +] 2026-08-04T10:13:15.564Z conn=conn-1 peer=127.0.0.1:7420
[CLIENT -> SERVER] 2026-08-04T10:13:15.567Z conn=conn-1 request=req-1 operation=PING bytes=36
[SERVER -> CLIENT] 2026-08-04T10:13:15.568Z conn=conn-1 request=req-1 status=200 phrase="OK" bytes=273
SLTP/1.0 200 OK  (273 bytes, 2 ms)
  Request-ID: req-1
  Server: SocketLens-TCP/0.1.2
  Timestamp: 2026-08-04T10:13:15.567Z
  Content-Type: application/json; charset=utf-8
  Content-Length: 100

Raw request bytes
  SLTP/1.0 PING\r\n
  Request-ID: req-1\r\n
  \r\n
```

**สิ่งที่ต้องชี้ให้ดู** (ชี้ด้วยเมาส์หรือเลเซอร์ทีละจุด)

1. หัวข้อ `[CLIENT -> SERVER]` และ `[SERVER -> CLIENT]` — ทั้งสองฝั่งพิมพ์ข้อความที่รับส่งจริง
2. บรรทัดเริ่มต้น `SLTP/1.0 PING` — นี่คือโปรโตคอลที่ผมออกแบบเอง ไม่ใช่ `GET / HTTP/1.1`
3. **`Request-ID: req-1` ปรากฏทั้งในคำขอและคำตอบ** — เป็นกลไกจับคู่ ทำให้ส่งหลายคำขอพร้อมกัน
   บนการเชื่อมต่อเดียวแล้วจับคู่คำตอบได้ถูกต้อง แม้เซิร์ฟเวอร์จะตอบไม่เรียงลำดับ
4. `\r\n` ปรากฏชัดเจนท้ายทุกบรรทัด และ `\r\n\r\n` คือตัวคั่นที่บอกว่าส่วนหัวจบแล้ว

**ประโยคเชื่อม** "ตอนนี้เห็นไบต์จริงแล้ว ต่อไปมาสร้างเซสชันเพื่อทดสอบกัน"

## ขั้นตอนที่ 2 — สร้างเซสชันและกฎจำลอง (25 วินาที)

> **พิสูจน์อะไร** ความหมายของสถานะและเซสชันในโพรโทคอล — `CREATE_SESSION` คืน
> `201 SESSION CREATED` พร้อมพอร์ต TCP จริงของเซสชัน และ `ADD_RULE` กำหนดว่า
> ปลายทางจะตอบอะไร เพื่อให้ทดสอบพฤติกรรมของโพรโทคอลได้

```bash
npm run cli -- session create --name demo-th
```

**ผลลัพธ์จริงที่ได้**

```
[SERVER -> CLIENT] ... session=ses-3 status=201 phrase="SESSION CREATED" bytes=429
✔ Session ses-3 created (201 SESSION CREATED).
  id            : ses-3
  name          : demo-th
  state         : active
  mock endpoint : 127.0.0.1:4045
  rules         : 0
  results       : 0
Its mock endpoint listens on 127.0.0.1:4045; scenarios connect there over raw TCP.
```

**สิ่งที่ต้องชี้ให้ดู**

- `201 SESSION CREATED` — เป็นรหัสสถานะของ SLTP ที่ผมนิยามเอง
- **`mock endpoint : 127.0.0.1:4045`** ← จุดสำคัญ

**สิ่งที่ต้องพูด**

"ทุกเซสชันได้พอร์ต TCP จริงของตัวเอง ที่ระบบปฏิบัติการจัดสรรให้ ผมเลือกทำแบบนี้เพราะ
ถ้าจำลองการแบ่งข้อความในหน่วยความจำ มันจะเป็นแค่การแกล้งทำ แต่เมื่อเป็นซ็อกเก็ตจริง
การเรียก `write()` เจ็ดครั้งของตัวอย่างที่ 5 จะผ่านสแต็ก TCP ของระบบปฏิบัติการจริง ๆ
และ**ระบบปฏิบัติการเป็นผู้ตัดสินว่าจะรวมหรือแยกเป็นกี่เซกเมนต์ ไม่ใช่ผม**
ความไม่แน่นอนนั้นคือสิ่งที่โพรโทคอลต้องรับมือให้ได้"

ต่อไปติดตั้งกฎจำลอง

```bash
npm run cli -- rule add --name pong --operation PING --status 200 \
  --body '{"message":"pong","note":"ตอบกลับ"}'
```

**ผลลัพธ์จริงที่ได้**

```
[SERVER -> CLIENT] ... status=212 phrase="RULE ADDED" bytes=522
✔ 212 RULE ADDED: rule "pong" installed.
  id              : rule-2
  name            : pong
  enabled         : true
  priority        : 0
  sequence        : 1
  match operation : PING
  response        : 200 OK
  response body   : {"message":"pong","note":"ตอบกลับ"}
```

**สิ่งที่ต้องชี้ให้ดู**

- `212 RULE ADDED` — SLTP มีรหัสเฉพาะสำหรับการเพิ่มกฎ ไม่ได้ใช้ 200 ทุกกรณี
- `priority: 0` และ `sequence: 1` — สองค่านี้กำหนดลำดับการประเมิน
  เรียงตาม priority จากมากไปน้อย เท่ากันจึงเรียงตาม sequence ลำดับจึงแน่นอนและทำซ้ำได้เสมอ
- **เนื้อความมีภาษาไทย** ซึ่งจะใช้เป็นตัวอย่างเรื่อง byte กับ character ในขั้นตอนถัดไป

**ถ้ามีเวลาเหลือ ให้เสริมประโยคนี้** "เนื้อความนี้มี 35 อักขระ แต่ยาว 49 ไบต์
เพราะอักษรไทยเจ็ดตัวใช้ตัวละ 3 ไบต์ `Content-Length` ของ SLTP นับเป็นไบต์เสมอ
ถ้าใช้ `str.length` ผู้รับจะอ่านขาดไป 14 ไบต์ แล้วสตรีมทั้งเส้นจะเสียหาย"

## ขั้นตอนที่ 3 — การแบ่งข้อความ ⭐ (60 วินาที)

> **พิสูจน์อะไร** การกำหนดขอบเขตข้อความถูกต้องบนสตรีมไบต์ของ TCP (FR-3, NFR-1)
> หนึ่งข้อความที่เขียนหลายครั้งต้องถูกประกอบกลับเป็นหนึ่งข้อความเสมอ

> นี่คือจุดที่สำคัญที่สุดของการนำเสนอทั้งหมด ห้ามรีบและห้ามข้าม

```bash
npm run cli -- run examples/05-fragmented-message/bundle.json
```

**ผลลัพธ์จริงที่ได้**

```
PASSED  seven-fragments  res-7
  writes out       : 7
  reads in         : 1
  responses framed : 1

Wire writes and reads
  → +0ms  6 bytes   SLTP/1
  → +26ms 14 bytes  .0 PING\r\nReque
  → +52ms 18 bytes  st-ID: req-frag-1\r
  ...
  ← +...  240 bytes SLTP/1.0 200 OK\r\n...

PASSED  byte-at-a-time  res-8
  writes out       : 134
  reads in         : 1
  responses framed : 1

2/2 scenario(s) passed
```

**สิ่งที่ต้องชี้ให้ดู — ทำตามลำดับนี้**

**ก่อนอื่น ชี้ที่ตัวเลขสามบรรทัดนี้**

```
writes out       : 7      ← เขียนเจ็ดครั้ง
reads in         : 1
responses framed : 1      ← ปลายทางได้ข้อความเดียว
```

**สิ่งที่ต้องพูด**

"นี่คือตัวอย่างที่ 5 สถานการณ์ `seven-fragments` ข้อความเดียวยาว 134 ไบต์
ผมส่งด้วยการเรียก `write()` เจ็ดครั้ง และตำแหน่งที่ตัดผมเลือกให้ยากที่สุด
เท่าที่จะทำได้

ส่วนแรกได้แค่ `SLTP/1` — ตัดกลางโทเคนของเวอร์ชัน
ส่วนที่สองจบที่ `Reque` — ตัดกลางชื่อส่วนหัว
มีจุดหนึ่งที่ผมตัด **ระหว่าง CR กับ LF ของตัวคั่นบรรทัดเดียวกัน**
และอีกจุดผมตัด **หนึ่งไบต์ก่อนตัวคั่นส่วนหัวจะครบสี่ไบต์**

ทุกจุดเป็นตำแหน่งที่โค้ดที่เขียนแบบสมมติเอาเองจะพังทันที แต่ตัวถอดรหัสยังประกอบได้ถูกต้อง"

**จากนั้นชี้ที่สถานการณ์ที่สอง**

```
writes out       : 134
responses framed : 1
```

"สถานการณ์ที่สองส่งทีละหนึ่งไบต์ 134 ครั้ง — ทุกไบต์เป็นการเรียก `write()` แยกกัน
ผลลัพธ์ยังคงเป็นข้อความเดียวที่ถูกต้อง ตัวถอดรหัสไม่ตั้งสมมติฐานใด ๆ เกี่ยวกับขนาดของข้อมูลที่ได้รับ"

**ประโยคปิดขั้นตอนนี้** "นี่คือครึ่งแรกของสิ่งที่ต้องการพิสูจน์ — หนึ่งข้อความอาจมาถึงเป็นหลายชิ้น"

## ขั้นตอนที่ 4 — การรวมข้อความ ⭐ (45 วินาที)

> **พิสูจน์อะไร** TCP ไม่รักษาขอบเขตข้อความระดับแอปพลิเคชัน — สิ่งเดียวที่บอกว่า
> ข้อความแรกจบตรงไหนคือ `Content-Length` ของมันเอง (FR-2)

```bash
npm run cli -- run examples/06-coalesced-messages/bundle.json
```

**ผลลัพธ์จริงที่ได้**

```
PASSED  two-messages-one-write  res-9
  writes out       : 1
  reads in         : 1
  responses framed : 2
```

**สิ่งที่ต้องชี้ให้ดู**

```
writes out       : 1      ← เขียนครั้งเดียว
responses framed : 2      ← ได้สองคำตอบ
```

**สิ่งที่ต้องพูด**

"ขั้นตอนที่แล้วคือหนึ่งข้อความมาถึงเป็นเจ็ดชิ้น ขั้นตอนนี้ตรงกันข้าม

ผมเรียก `write()` ครั้งเดียว แต่ในนั้นมีข้อความ SLTP สองข้อความติดกัน และปลายทางแยกออกได้ถูกต้อง
ตอบกลับมาสองคำตอบ

การแยกนี้อาศัย `Content-Length` ล้วน ๆ ตัวถอดรหัสอ่านความยาวของข้อความแรก ตัดไบต์ตามจำนวนนั้น
แล้ววนกลับไปตรวจว่าในบัฟเฟอร์ยังมีข้อความถัดไปอยู่หรือไม่

ถ้าลืมวนกลับ ข้อความที่สองจะค้างในบัฟเฟอร์และไม่มีวันถูกประมวลผล เพราะเหตุการณ์ `data`
ที่จะมากระตุ้นอาจไม่มีอีกแล้ว นี่คือบั๊กที่หาเจอยากมากในระบบจริง

และถ้าเขียนโค้ดแบบสไลด์ที่สองที่ผมแสดงตอนต้น ข้อความที่สองจะหายไปเงียบ ๆ โดยไม่มีข้อผิดพลาดใด ๆ"

**สิ่งที่ต้องพูด — เตรียมไว้ตอบคำถามล่วงหน้า**

"สังเกตว่า 211 อยู่ในกลุ่ม 2xx ซึ่งเป็นกลุ่มสำเร็จ ผมออกแบบไว้อย่างนี้โดยตั้งใจ

รหัสสถานะของ SLTP อธิบายผลของคำขอ SLTP ไม่ได้อธิบายผลของการทดสอบ
เซิร์ฟเวอร์รับคำขอ รันสถานการณ์ได้ เก็บผลได้ และตอบกลับครบถ้วน — คำขอนั้นสำเร็จโดยสมบูรณ์
การที่ผลไม่ตรงเป้าเป็นเนื้อหาของคำตอบ ไม่ใช่ความล้มเหลวของโปรโตคอล

ถ้าสถานการณ์เขียนผิดจนรันไม่ได้เลย นั่นจะเป็น 422 INVALID SCENARIO ซึ่งอยู่ในกลุ่ม 4xx อย่างถูกต้อง"

### 5.3 การหมดเวลา

```bash
npm run cli -- run examples/08-timeout/bundle.json
```

ชี้ให้ดูว่ากฎหน่วง 2500 ms ขณะที่สถานการณ์กำหนด timeout ไว้ 500 ms
สถานการณ์นี้ระบุ `expect: { timeout: true }` จึงถือว่าผ่าน เพราะการหมดเวลาคือสิ่งที่ตั้งใจทดสอบ

### 5.4 Content-Length ที่ผิดรูปแบบ

```bash
npm run cli -- run examples/09-malformed-content-length/bundle.json
```

**สิ่งที่ต้องชี้ให้ดู**

- `Content-Length: abc` → `400 BAD REQUEST` พร้อม `Reason: invalid-content-length`
- `Content-Length: -1` → `400 BAD REQUEST` พร้อม `Reason: negative-content-length`
- ทุกกรณีมีส่วนหัว **`Connection: close`**
- **สถานการณ์ถัดไปในไฟล์เดียวกันยังรันต่อได้** แสดงว่าเซิร์ฟเวอร์ไม่ได้ล้ม

**สิ่งที่ต้องพูด**

"เมื่อ `Content-Length` ใช้การไม่ได้ ผมไม่รู้ว่าเนื้อความจบตรงไหน จึงไม่รู้ว่าข้อความถัดไปเริ่มตรงไหน
ถ้าเดาแล้วเดาผิด ไบต์ของเนื้อความจะถูกอ่านเป็นบรรทัดเริ่มต้นใหม่ เกิดข้อผิดพลาดต่อเนื่องไม่จบสิ้น
สภาวะนี้เรียกว่า decoder poisoning

การปิดการเชื่อมต่อจึงเป็นทางเลือกเดียวที่ตรงไปตรงมา แต่สังเกตว่าปิดเฉพาะการเชื่อมต่อนั้น
เซิร์ฟเวอร์ยังให้บริการรายอื่นตามปกติ — ทุกการเชื่อมต่อมีบัฟเฟอร์และตัวถอดรหัสเป็นของตัวเอง"

## ขั้นตอนที่ 6 — จับแพ็กเก็ตด้วย Wireshark ⭐ (135 วินาที)

> **พิสูจน์อะไร** SLTP ปรากฏบนสตรีม TCP จริงอย่างไร และขอบเขตการเขียนของแอปพลิเคชัน
> ไม่เท่ากับขอบเขตเซกเมนต์ที่ระบบปฏิบัติการสร้าง

> ต้องเริ่มจับแพ็กเก็ตไว้ก่อนขึ้นเวที และตั้งตัวกรอง `tcp.port == 7420` ไว้แล้ว
> ขั้นตอนละเอียดทั้งหมดอยู่ใน [wireshark-capture.md](wireshark-capture.md)

**ประโยคเปิด**

"ที่ผ่านมาทั้งหมดคือล็อกที่โปรแกรมของผมพิมพ์ออกมาเอง ต่อไปนี้ผมจะแสดงหลักฐานจากเครื่องมือ
ภายนอกที่ไม่รู้จักโปรโตคอลของผมเลย"

### 6.1 คำขอเดียว อ่านทั้งข้อความบนสาย (30 วินาที)

**เทอร์มินัล B**

```bash
npm run wireshark:demo -- --scenario ping
```

ผลลัพธ์จะพิมพ์ **พอร์ตฝั่งเครื่องเรา** และตัวกรองที่คัดลอกไปวางใน Wireshark ได้ทันที

```
[1] ping — one request, one response
  target          127.0.0.1:7420  (control server)
  local           127.0.0.1:13049
  Request-ID      ws-ping
  request         38 bytes in 1 application write
  response        200 OK, 271 bytes
  filter          tcp.port == 13049
```

จากนั้นใน Wireshark คลิกขวาที่แพ็กเก็ตใดก็ได้ → **Follow → TCP Stream**

**สิ่งที่ต้องชี้ให้ดู ตามลำดับนี้**

| ลำดับ | ชี้ที่           | พูดว่า                                                           |
| ----- | ---------------- | ---------------------------------------------------------------- |
| 1     | `SLTP/1.0 PING`  | "บรรทัดเริ่มต้นของเราเอง ไม่มีเมท็อด ไม่มีพาธ ไม่มี `Host`"      |
| 2     | `Request-ID`     | "ค่าเดียวกันทั้งสองทิศทาง คำตอบจึงกลับมาไม่ตามลำดับได้"          |
| 3     | `Content-Length` | "นับเป็นไบต์ ไม่ใช่อักขระ นับไบต์หลังบรรทัดว่างได้เลย"           |
| 4     | บรรทัดว่าง       | "ในมุมมองนี้เห็นเป็นบรรทัดว่าง แต่บนสายคือสี่ไบต์ `0d 0a 0d 0a`" |

**ประโยคที่ต้องพูด** "อ่านออกทั้งหมดโดยไม่ต้องมี dissector เพราะส่วนหัวของ SLTP เป็น
US-ASCII ที่พิมพ์ได้ เป็นการออกแบบที่ตั้งใจ และการจับแพ็กเก็ตคือจุดที่มันคุ้มค่า"

### 6.2 การเขียนไม่เท่ากับเซกเมนต์ ⭐⭐ (45 วินาที)

```bash
npm run wireshark:demo -- --scenario fragmentation
```

เทอร์มินัลรายงาน `135 bytes in 6 application writes` พร้อมขนาดแต่ละชิ้น
`6 + 14 + 18 + 24 + 40 + 33` และหน่วง 30 มิลลิวินาทีระหว่างการเขียน

จากนั้นใน Wireshark ใส่ตัวกรอง `tcp.len > 0` แล้ว **นับเซกเมนต์ที่มีเพย์โหลดในสตรีมนั้น**

**สิ่งที่ต้องพูด — นี่คือประโยคที่สำคัญที่สุดของทั้งการนำเสนอ**

"ในสถานการณ์ `fragmentation` ของตัวสร้างทราฟฟิกนี้ โปรแกรมเรียก `socket.write()` หกครั้ง
นั่นเป็นข้อเท็จจริงของโปรแกรม
แต่จำนวนเซกเมนต์ TCP ที่บรรจุไบต์เหล่านั้นเป็นการตัดสินใจของระบบปฏิบัติการ
ขึ้นกับอัลกอริทึมของ Nagle หน้าต่างความคับคั่ง และ MTU ของเส้นทาง

บน loopback ของ Windows ค่า MSS ใหญ่มากถึงระดับหลายหมื่นไบต์ ข้อความทั้งข้อความจึงใส่
ในเซกเมนต์เดียวได้สบาย สิ่งที่ทำให้การเขียนหกครั้งไม่ถูกรวมเข้าด้วยกันคือการหน่วง
30 มิลลิวินาที ถ้าไม่หน่วงมันจะถูกรวมแทบแน่นอน

แต่ไม่ว่าจะได้กี่เซกเมนต์ ปลายทางประกอบได้ **หนึ่งข้อความ** เสมอ เทอร์มินัลยืนยันไว้ว่า
`framed 1 complete SLTP message(s)`"

**ห้ามพูดผิด** อย่าพูดว่า "เขียนหกครั้งคือหกแพ็กเก็ต" เพราะไม่จริง และกรรมการที่รู้เรื่อง TCP
จะจับได้ทันที ให้พูดว่า "เขียนหกครั้ง" เสมอ และระวังไม่สลับกับตัวอย่างที่ 5 ในขั้นตอนที่ 3
ซึ่งเป็นการเขียนเจ็ดครั้ง — เป็นการสาธิตคนละอันกัน

### 6.3 การรวมข้อความบนสาย ⭐ (30 วินาที)

```bash
npm run wireshark:demo -- --scenario coalescing
```

Follow TCP Stream แล้วชี้ที่รอยต่อระหว่างสองข้อความ

```
{"echo":"first"}SLTP/1.0 PING
Request-ID: ws-coal-b
```

**สิ่งที่ต้องพูด** "ข้อความที่สองเริ่มทันทีหลังเนื้อความของข้อความแรก **ไม่มีตัวคั่น
ไม่มีเครื่องหมาย ไม่มีช่องว่าง** สิ่งเดียวที่บอกว่าข้อความแรกจบที่ไหนคือ `Content-Length`
ของมันเอง

รวมกับข้อ 6.2 นี่คือการให้เหตุผลที่ครบถ้วน — เขียนครั้งเดียวได้สองข้อความ
เขียนหกครั้ง (ในสถานการณ์ `fragmentation` ของข้อ 6.2) ได้ข้อความเดียว
ไม่มีอะไรในระดับซ็อกเก็ตแยกสองกรณีนี้ออกจากกันได้"

### 6.4 ความล้มเหลวหนึ่งกรณี (30 วินาที)

```bash
npm run wireshark:demo -- --scenario malformed
```

**สิ่งที่ต้องชี้ให้ดู**

- คำตอบ `400 BAD REQUEST` พร้อมส่วนหัว `Connection: close` และ `Reason`
- ตามด้วย **FIN** จริง ใส่ตัวกรอง `tcp.flags.fin == 1` เพื่อให้เห็นชัด

**สิ่งที่ต้องพูด** "`Content-Length: -5` ใช้หาจุดจบของเนื้อความไม่ได้ สตรีมจึงซิงโครไนซ์
กลับไม่ได้ เพราะไม่รู้ว่าข้อความถัดไปเริ่มที่ไบต์ไหน เราจึงบอกไปตรง ๆ ด้วยส่วนหัว
แล้วปิดการเชื่อมต่อ ไม่ปล่อยให้ปลายทางเดาจาก FIN เอง"

> **ถ้าเวลาเหลือ** เปิด `--scenario concurrent` แล้วเปิด **Statistics → Conversations → TCP**
> ให้เห็นสามสตรีมเรียงกัน พร้อมกล่าวว่าแต่ละการเชื่อมต่อมีตัวถอดรหัสและสถานะการกำหนดขอบเขต
> ของตัวเอง

## ประโยคปิดการสาธิต

"สรุปสิ่งที่เห็นวันนี้

ข้อความเดียวส่งด้วยการเขียนเจ็ดครั้ง (ตัวอย่างที่ 5 `seven-fragments`) — ปลายทางได้ข้อความเดียว
ข้อความเดียวส่งทีละหนึ่งไบต์ 134 ครั้ง (ตัวอย่างที่ 5 `byte-at-a-time`) — ปลายทางยังได้ข้อความเดียว
สองข้อความส่งด้วยการเขียนครั้งเดียว (ตัวอย่างที่ 6) — ปลายทางได้สองข้อความ

สามกรณีนี้พิสูจน์ประโยคเดียวกัน คือ **TCP เป็นสตรีมไบต์ที่เชื่อถือได้และรักษาลำดับ
แต่ไม่รักษาขอบเขตของข้อความระดับแอปพลิเคชัน** และตัวถอดรหัสที่ถูกต้องต้องรับมือได้ทุกกรณี

และข้อสุดท้าย Wireshark ยืนยันว่าไบต์บนสายเป็นอย่างที่โปรแกรมรายงานจริง พร้อมแสดงว่า
**จำนวนการเขียน จำนวนเซกเมนต์ และจำนวนข้อความเป็นสามค่าที่ต่างกัน**"

| เวลาที่เหลือ | ให้ตัดอะไร                                     |
| ------------ | ---------------------------------------------- |
| เหลือ 5 นาที | ตัดขั้นตอนที่ 5.3 และ 5.4                      |
| เหลือ 4 นาที | ตัดขั้นตอนที่ 5 ทั้งหมด และตัด 6.4             |
