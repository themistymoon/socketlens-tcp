# คำถามที่คาดว่าจะถูกถามและแนวคำตอบ

เอกสารนี้รวบรวมคำถามที่มีโอกาสถูกถามในการนำเสนอ พร้อมแนวคำตอบที่อ้างอิงจากการทำงานจริงของระบบ
จัดกลุ่มตามหัวข้อและเรียงตามโอกาสที่จะถูกถามจากมากไปน้อยภายในแต่ละกลุ่ม

**หลักการตอบคำถาม**

1. ตอบประโยคแรกให้ตรงคำถามทันที แล้วค่อยขยายความ
2. หากเป็นการตัดสินใจเชิงออกแบบ ให้บอกทางเลือกที่พิจารณาแล้วไม่เลือก พร้อมเหตุผล
3. **หากไม่ทราบ ให้ตอบว่าไม่ทราบ** แล้วบอกว่าจะหาคำตอบอย่างไร การเดาแล้วผิดเสียหายกว่ามาก
4. อย่ากล่าวเกินจริงเกี่ยวกับสิ่งที่ระบบทำได้

## กลุ่มที่ 1 — การเลือกโพรโทคอลขนส่ง

### ถาม 1.1 ⭐ ทำไมถึงเลือก TCP ไม่เลือก UDP

**แนวคำตอบ**

"เหตุผลหลักคือสิ่งที่ผมต้องการศึกษาอยู่ที่ TCP เอง

วัตถุประสงค์ของโครงงานคือแสดงให้เห็นว่า TCP เป็นสตรีมไบต์ที่ไม่รักษาขอบเขตข้อความ
ปัญหานี้เป็นปัญหาเฉพาะของโปรโตคอลแบบสตรีม ถ้าใช้ UDP ปัญหานี้จะหายไปทันที
เพราะ UDP เป็นดาตาแกรม หนึ่งดาตาแกรมที่ส่งคือหนึ่งดาตาแกรมที่รับ ตัวถอดรหัสแบบเพิ่มทีละส่วน
ซึ่งเป็นงานทางเทคนิคที่สำคัญที่สุดของโครงงานจะไม่มีความจำเป็นเลย

นอกจากนั้นยังมีเหตุผลทางวิศวกรรมอีกสามข้อ

ข้อแรก ข้อความของผมมีขนาดตั้งแต่ศูนย์ไบต์ถึง 1 MiB ถ้าใช้ UDP ดาตาแกรมที่ใหญ่เกิน MTU
จะถูกแบ่งที่ชั้น IP และถ้าชิ้นส่วนใดหาย ทั้งก้อนใช้ไม่ได้

ข้อสอง ผมต้องการความครบถ้วนและลำดับ ถ้าส่วนหัวหายไปแค่ส่วนเดียว ผู้รับจะไม่รู้ว่าเนื้อความจบตรงไหน

ข้อสาม รูปแบบการสื่อสารเป็นคำขอกับคำตอบที่มีสถานะต่อเนื่อง เซสชันและกฎผูกกับการเชื่อมต่อ
การเชื่อมต่อที่คงอยู่ของ TCP เข้ากับรูปแบบนี้โดยธรรมชาติ

ถ้าเลือก UDP ผมจะต้องสร้างกลไกตอบรับ กลไกส่งซ้ำ และกลไกจับเวลาขึ้นมาเอง
ซึ่งเท่ากับสร้าง TCP ใหม่ในเวอร์ชันที่แย่กว่า"

### ถาม 1.2 UDP มีข้อดีที่รักษาขอบเขตข้อความอยู่แล้ว ไม่ใช่หรือ

**แนวคำตอบ**

"ใช่ครับ และนั่นคือเหตุผลที่ผมไม่เลือกมันในโครงงานนี้

ในบริบททั่วไปมันเป็นข้อดี แต่ในบริบทของโครงงานนี้มันทำให้ปัญหาที่ผมต้องการศึกษาหายไป
ถ้า UDP แก้ปัญหาให้แล้ว ผมก็ไม่มีอะไรจะสาธิต

พูดอีกอย่างคือ ผมเลือก TCP เพราะมันมีปัญหานี้ ไม่ใช่ทั้ง ๆ ที่มันมีปัญหานี้

ผมระบุ UDP ไว้ในแผนพัฒนาต่อ แต่ในฐานะ **หัวข้อเปรียบเทียบ** ให้ผู้เรียนเห็นความต่างระหว่าง
ดาตาแกรมกับสตรีม ไม่ใช่ในฐานะสิ่งทดแทน"

### ถาม 1.3 ถ้าเป็นแอปพลิเคชันจริงที่ต้องการความเร็วสูง จะเลือกอย่างไร

**แนวคำตอบ**

"ขึ้นอยู่กับว่ายอมเสียข้อมูลได้หรือไม่

ถ้าเป็นสตรีมมิงเสียงหรือวิดีโอ หรือเกมที่ส่งตำแหน่งผู้เล่นถี่ ๆ ข้อมูลเก่าไม่มีค่าเมื่อข้อมูลใหม่มาแล้ว
UDP เหมาะกว่า เพราะการส่งซ้ำของ TCP จะทำให้เกิด head-of-line blocking คือข้อมูลใหม่ต้องรอ
ข้อมูลเก่าที่หายไปถูกส่งซ้ำก่อน ซึ่งไม่มีประโยชน์เลยในกรณีนี้

แต่ถ้าทุกไบต์มีความหมาย เช่น การทำธุรกรรม การถ่ายโอนไฟล์ หรือกรณีของผมที่ถ้าส่วนหัวหาย
ผู้รับจะกู้ตำแหน่งข้อความถัดไปไม่ได้เลย TCP เป็นทางเลือกที่ถูกต้อง

สำหรับเครื่องมือนี้ซึ่งทำงานบน loopback ความเร็วไม่ใช่ข้อจำกัดอยู่แล้วครับ"

## กลุ่มที่ 2 — การออกแบบโปรโตคอล

### ถาม 2.1 ⭐ ทำไม 211 TEST FAILED ถึงอยู่ในกลุ่ม 2xx ไม่ใช่ 4xx หรือ 5xx

**แนวคำตอบ**

"เพราะรหัสสถานะอธิบายผลของ **คำขอ SLTP** ไม่ได้อธิบายผลของ **การทดสอบ**

เมื่อไคลเอนต์ส่ง RUN_TEST แล้วเซิร์ฟเวอร์รับคำขอได้ แจงได้ รันสถานการณ์ได้ เก็บผลได้
และตอบกลับครบถ้วน แปลว่าคำขอ SLTP นั้นสำเร็จโดยสมบูรณ์ ไม่มีอะไรผิดพลาดในระดับโปรโตคอลเลย
การที่ผลเปรียบเทียบออกมาไม่ตรงกับที่คาดหวังเป็นเพียงเนื้อหาของคำตอบ

เปรียบเทียบให้เห็นภาพ การทดสอบที่ไม่ผ่านก็เหมือนการวัดที่ได้ค่าไม่ตรงเป้า การวัดนั้นสำเร็จ
ส่วนค่าที่ได้เป็นอีกเรื่องหนึ่ง

ถ้าผมใช้ 4xx สำหรับ 211 ไคลเอนต์จะแยกไม่ออกระหว่าง 'ทดสอบแล้วไม่ผ่าน' กับ
'คำขอผิดพลาดจนรันไม่ได้' ซึ่งเป็นสองเรื่องที่ต้องจัดการต่างกันโดยสิ้นเชิง

กรณีที่สถานการณ์ทดสอบเขียนผิดจนรันไม่ได้เลย ผมใช้ 422 INVALID SCENARIO ซึ่งอยู่ใน 4xx
อย่างถูกต้อง เพราะกรณีนั้นคำขอมีปัญหาจริง"

### ถาม 2.2 ⭐ รหัสสถานะเหล่านี้ลอกมาจาก HTTP หรือเปล่า

**แนวคำตอบ**

"ไม่ครับ ผมยืมเฉพาะ **ช่วงตัวเลข** มาเพื่อความคุ้นเคย แต่ความหมายทุกรหัสผมนิยามเองภายใต้บริบทของ SLTP

หลักฐานชัดเจนคือมีหลายรหัสที่ไม่มีใน HTTP เลย เช่น
210 TEST PASSED, 211 TEST FAILED, 212 RULE ADDED, 213 RULE UPDATED, 214 RULE DELETED
และ 410 NO MATCHING RULE ซึ่งใน HTTP หมายถึง Gone แต่ใน SLTP หมายถึงปลายทางจำลอง
ไม่พบกฎที่ตรงกับคำขอ

แม้รหัสที่หมายเลขตรงกัน ความหมายก็เป็นของ SLTP เอง เช่น 404 ใน SLTP คือ SESSION NOT FOUND
ไม่ใช่ Not Found ทั่วไป และ 413 คือข้อความเกินขีดจำกัด 1 MiB ที่ผมกำหนดไว้เอง

ทะเบียนรหัสสถานะอยู่ในไฟล์ `packages/protocol/src/status.ts` ซึ่งเป็นแหล่งอ้างอิงหลัก
และเอกสาร `docs/status-codes.md` อธิบายทุกรหัสพร้อมบริบทที่ใช้"

### ถาม 2.3 ⭐ ทำไม Content-Length ต้องนับเป็นไบต์ ไม่นับเป็นอักขระ

**แนวคำตอบ**

"เพราะสิ่งที่วิ่งบนสายคือไบต์ ไม่ใช่อักขระ

ยกตัวอย่างจากที่สาธิตไปเมื่อสักครู่ เนื้อความ `{"message":"pong","note":"ตอบกลับ"}`
มี 35 อักขระ แต่ยาว 49 ไบต์ เพราะอักษรไทยเจ็ดตัวใช้ตัวละ 3 ไบต์ในการเข้ารหัส UTF-8
รวม 21 ไบต์ บวกอักขระ ASCII อีก 28 ตัว ได้ 49

ถ้าผมส่ง `Content-Length: 35` ผู้รับจะอ่านเนื้อความไป 35 ไบต์แล้วหยุด ทั้งที่เนื้อความจริงยาว 49
เหลืออีก 14 ไบต์ค้างในบัฟเฟอร์ แล้วตัวถอดรหัสจะพยายามอ่าน 14 ไบต์นั้นเป็นบรรทัดเริ่มต้น
ของข้อความถัดไป ซึ่งแน่นอนว่าไม่ใช่ ผลคือสตรีมทั้งเส้นเสียหายต่อเนื่องไปไม่มีที่สิ้นสุด

จุดที่อันตรายคือใน JavaScript `str.length` คืนจำนวนหน่วยรหัส UTF-16 ไม่ใช่จำนวนไบต์
ผมจึงใช้ `Buffer.byteLength(body, 'utf8')` เสมอ

และที่สำคัญคือ ถ้าเนื้อความเป็นภาษาอังกฤษล้วน สองค่านี้จะเท่ากันพอดี บั๊กนี้จึงซ่อนตัวได้นาน
จนกว่าจะมีคนพิมพ์ภาษาไทยหรืออีโมจิเข้ามา"

### ถาม 2.4 ทำไมใช้ CRLF ไม่ใช้ LF อย่างเดียว

**แนวคำตอบ**

"เหตุผลหลักคือความชัดเจนในการกำหนดขอบเขต

ตัวคั่นสองไบต์ `\r\n\r\n` มีโอกาสปรากฏโดยบังเอิญในข้อมูลน้อยกว่าตัวคั่นไบต์เดียว
และเมื่อไล่ดูไบต์ด้วยตาหรือด้วย hex dump มันเห็นชัดกว่า

เหตุผลรองคือความสอดคล้องกับโปรโตคอลข้อความบนอินเทอร์เน็ตส่วนใหญ่ ทำให้ผู้ที่คุ้นเคย
กับโปรโตคอลอื่นอ่าน SLTP ได้ทันที

ข้อเสียคือเปลืองไปหนึ่งไบต์ต่อบรรทัด ซึ่งในบริบทของเครื่องมือทดสอบบนเครื่องเดียวไม่มีนัยสำคัญ

จุดที่น่าสนใจคือ CRLF ทำให้เกิดกรณีทดสอบที่ยากขึ้นมาหนึ่งกรณี คือการแบ่งข้อมูล **ระหว่าง CR กับ LF**
ซึ่งผมทดสอบไว้โดยเจตนา และเป็นหนึ่งในจุดตัดของตัวอย่างที่ 5 ที่สาธิตไปแล้ว"

### ถาม 2.5 ทำไมต้องมี Request-ID ในเมื่อ TCP รักษาลำดับอยู่แล้ว

**แนวคำตอบ**

"เพราะลำดับของ TCP รับประกันแค่ว่าไบต์มาถึงตามลำดับ แต่ไม่ได้บังคับว่าเซิร์ฟเวอร์ต้องตอบตามลำดับที่รับ

ถ้าไคลเอนต์ส่งคำขอสามรายการติดกันโดยไม่รอคำตอบ แล้วคำขอที่สองใช้เวลาประมวลผลนาน
เซิร์ฟเวอร์อาจตอบรายการที่หนึ่งและสามก่อน `Request-ID` ทำให้จับคู่ได้ถูกต้องเสมอ

นอกจากนี้ยังมีประโยชน์ในการติดตามปัญหา เพราะล็อกทั้งสองฝั่งมี `Request-ID` เดียวกัน
ทำให้ไล่ดูได้ว่าคำขอไหนคู่กับคำตอบไหน

ในชุดทดสอบมีกรณีที่ยืนยันว่าคำขอหลายรายการบนการเชื่อมต่อเดียวถูกจับคู่ถูกต้องแม้ตอบสลับลำดับ"

### ถาม 2.6 ทำไมไม่ใช้ JSON ทั้งข้อความไปเลย จะได้ง่ายกว่า

**แนวคำตอบ**

"เพราะ JSON แก้ปัญหาการกำหนดขอบเขตไม่ได้ครับ

ถ้าส่ง JSON ล้วนบน TCP ผู้รับก็ยังไม่รู้อยู่ดีว่า JSON จบตรงไหน ทางออกมีสองแบบ
แบบแรกคือนับวงเล็บปีกกาให้สมดุล ซึ่งต้องระวังวงเล็บที่อยู่ในสตริงและ escape sequence
แบบที่สองคือใส่ความยาวไว้ข้างหน้า ซึ่งก็คือสิ่งที่ผมทำอยู่แล้ว

การมีส่วนหัวแยกจากเนื้อความยังมีข้อดีอีกข้อ คือผมอ่าน `Content-Length` ได้โดยไม่ต้องแจงเนื้อความ
ถ้าความยาวเกินขีดจำกัด ผมปฏิเสธได้ทันทีโดยไม่ต้องรับข้อมูลเข้ามาทั้งหมดก่อน
ซึ่งเป็นการป้องกันการใช้หน่วยความจำเกินตัว

เนื้อความของ SLTP ใช้ JSON อยู่แล้วครับ แต่ **การกำหนดขอบเขตอยู่คนละชั้นกับการเข้ารหัสข้อมูล**"

## กลุ่มที่ 3 — ความถูกต้องทางเทคนิคของ TCP

### ถาม 3.1 ⭐ ตัวถอดรหัสทำงานอย่างไร อธิบายขั้นตอนได้ไหม

**แนวคำตอบ**

"ตัวถอดรหัสทำงานแยกกันต่อหนึ่งการเชื่อมต่อ แต่ละการเชื่อมต่อมีบัฟเฟอร์ของตัวเอง
ขั้นตอนเมื่อได้รับข้อมูลก้อนใหม่มีดังนี้

ขั้นแรก ต่อข้อมูลใหม่เข้ากับบัฟเฟอร์เดิม

จากนั้นเข้าลูป
ค้นหา `\r\n\r\n` ถ้าไม่พบแปลว่าส่วนหัวยังมาไม่ครบ ให้เก็บไว้รอก้อนถัดไปแล้วออกจากลูป
ถ้าพบ ก็แจงบรรทัดเริ่มต้นและส่วนหัว อ่านค่า `Content-Length` และตรวจความถูกต้อง
แล้วดูว่าไบต์ในบัฟเฟอร์ครบตามความยาวนั้นหรือยัง ถ้ายังไม่ครบก็เก็บไว้รอ
ถ้าครบแล้วจึงส่งออกข้อความสมบูรณ์หนึ่งข้อความ ตัดไบต์ที่ใช้ไปแล้วออก **แล้ววนกลับไปข้อแรก**

จุดที่สำคัญที่สุดคือการวนกลับ เพราะในบัฟเฟอร์อาจมีข้อความถัดไปรออยู่แล้ว
ถ้าลืมวน ข้อความที่สองจะค้างและไม่ถูกประมวลผลจนกว่าจะมีข้อมูลใหม่มากระตุ้น ซึ่งอาจไม่มีวันมา

อีกจุดหนึ่งคือทุกอย่างทำบน Buffer ไม่ใช่สตริง เพราะการแปลงเป็นสตริงก่อนข้อมูลครบ
จะทำให้อักขระ UTF-8 หลายไบต์ที่ถูกแบ่งกลางตัวเสียหายถาวร ผมแปลงเป็นข้อความ
เฉพาะตอนที่เนื้อความครบแล้วเท่านั้น"

### ถาม 3.2 ⭐ ทดสอบอย่างไรว่ารับมือการแบ่งข้อความได้จริง

**แนวคำตอบ**

"ทดสอบสามระดับครับ

ระดับที่หนึ่งคือทดสอบหน่วยของตัวถอดรหัส ผมป้อนข้อความเดียวกันแบ่งที่ตำแหน่งต่าง ๆ
รวมถึงกรณีที่ยากที่สุด คือแบ่งกลางบรรทัดเริ่มต้น แบ่งกลางชื่อส่วนหัว
**แบ่งระหว่าง CR กับ LF** แบ่งกลางตัวคั่นสี่ไบต์ และ **แบ่งกลางตัวอักษร UTF-8 แบบสามไบต์**

ระดับที่สองคือทดสอบบูรณาการด้วยซ็อกเก็ต TCP จริง

ระดับที่สามคือตัวอย่างที่รันได้จริง ซึ่งสาธิตไปแล้ว ตัวอย่างที่ 5 ส่งข้อความ 134 ไบต์
ด้วยการเขียนเจ็ดครั้ง โดยตำแหน่งตัดเลือกมาให้ยากที่สุด และอีกสถานการณ์ส่งทีละหนึ่งไบต์ 134 ครั้ง
ทั้งสองกรณีปลายทางประกอบได้เป็นข้อความเดียวถูกต้อง

การส่งทีละไบต์เป็นกรณีที่รุนแรงที่สุดที่เป็นไปได้ ถ้าผ่านกรณีนี้ได้ก็ผ่านทุกกรณี"

### ถาม 3.3 ถ้าผู้ส่งไม่ส่งข้อมูลจนครบ จะเกิดอะไรขึ้น

**แนวคำตอบ**

"มีสองสถานการณ์ที่ต้องแยกกัน

สถานการณ์แรก ผู้ส่งเงียบไปเฉย ๆ แต่การเชื่อมต่อยังอยู่ ตรงนี้ขีดจำกัดขนาดทำหน้าที่ป้องกัน
เพราะบัฟเฟอร์จะโตได้ไม่เกิน 1 MiB และไม่เกิน 16 KiB สำหรับบล็อกส่วนหัว
เกินเมื่อไรก็ปิดการเชื่อมต่อ ทางฝั่งไคลเอนต์ยังมี timeout อีกชั้นหนึ่งด้วย

สถานการณ์ที่สอง การเชื่อมต่อถูกตัดกลางคัน กรณีนี้ผมรายงานว่าเป็นข้อความที่ถูกตัดทอน
และ **ไม่พยายามแจงข้อมูลที่ไม่สมบูรณ์** เพราะการแจงครึ่ง ๆ กลาง ๆ อันตรายกว่าการยอมรับว่าไม่สมบูรณ์

ตัวอย่างที่ 10 สาธิตกรณีนี้ทั้งสองทิศทาง คือฝั่งไคลเอนต์ตัดหลังส่งไป 30 ไบต์
และฝั่งเซิร์ฟเวอร์ตัดหลังตอบไป 40 ไบต์"

### ถาม 3.4 ทำไมข้อผิดพลาดบางอย่างต้องปิดการเชื่อมต่อ แต่บางอย่างไม่ต้อง

**แนวคำตอบ**

"เกณฑ์มีข้อเดียวครับ คือหลังเกิดข้อผิดพลาดแล้ว ยังหาจุดเริ่มต้นของข้อความถัดไปได้หรือไม่

ถ้ายังหาได้ ถือว่ากู้คืนได้ ผมตอบข้อผิดพลาดแล้วเปิดการเชื่อมต่อไว้ต่อ เช่น ขาด `Request-ID`
ปฏิบัติการไม่มีในทะเบียน หรือเนื้อความไม่ใช่ JSON ที่ถูกต้อง กรณีเหล่านี้กรอบของข้อความยังสมบูรณ์
ผมรู้ว่าข้อความจบตรงไหน จึงอ่านข้อความถัดไปต่อได้

ถ้าหาไม่ได้ ถือว่าร้ายแรง ผมตอบข้อผิดพลาดพร้อมส่วนหัว `Connection: close` แล้วปิด
เช่น `Content-Length` ไม่ใช่ตัวเลข ติดลบ ซ้ำและขัดแย้งกัน หรือข้อความเกินขีดจำกัด

เหตุผลคือถ้า `Content-Length` ใช้การไม่ได้ ผมไม่รู้ว่าเนื้อความยาวเท่าไร จึงไม่รู้ว่าจะข้ามไปกี่ไบต์
ถ้าเดาแล้วผิด ไบต์ของเนื้อความจะถูกอ่านเป็นบรรทัดเริ่มต้นใหม่ เกิดข้อผิดพลาดต่อเนื่องไม่จบสิ้น
สภาวะนี้เรียกว่า decoder poisoning การปิดการเชื่อมต่อเป็นทางเลือกเดียวที่ตรงไปตรงมา

และการปิดกระทบเฉพาะการเชื่อมต่อนั้น เซิร์ฟเวอร์ยังให้บริการรายอื่นตามปกติ"

### ถาม 3.5 อัลกอริทึมของ Nagle เกี่ยวข้องกับงานนี้อย่างไร

**แนวคำตอบ**

"เกี่ยวข้องโดยตรงและเห็นผลจริงครับ

อัลกอริทึมของ Nagle พยายามลดจำนวนแพ็กเก็ตขนาดเล็ก โดยรวมข้อมูลที่เขียนติดกันหลายครั้ง
ไว้ในแพ็กเก็ตเดียว นี่คือสาเหตุที่พบบ่อยที่สุดในโลกจริงที่ทำให้หลายข้อความมาถึงพร้อมกัน

ในตัวอย่างที่ 5 ผมต้องกำหนด `interFragmentDelayMs` ไว้ประมาณ 25 มิลลิวินาที
เพราะถ้าเขียนเจ็ดครั้งติดกันโดยไม่หน่วงเลย เคอร์เนลอาจรวมทั้งเจ็ดส่วนกลับเป็นแพ็กเก็ตเดียว
ทำให้การสาธิตการแบ่งข้อความไม่เกิดผล

ประเด็นนี้น่าสนใจตรงที่ **ผมต้องต่อสู้กับ TCP เพื่อสาธิตพฤติกรรมของ TCP** ซึ่งยืนยันข้อสรุปหลัก
ของโครงงานอีกทางหนึ่ง คือโปรแกรมควบคุมไม่ได้ว่าข้อมูลจะมาถึงเป็นชิ้นขนาดเท่าไร
จึงต้องไม่ตั้งสมมติฐานใด ๆ ทั้งสิ้น"

### ถาม 3.6 ทำไมไม่ใช้ worker thread เพื่อรองรับหลายไคลเอนต์

**แนวคำตอบ**

"เพราะงานนี้เป็นงานที่รอ input/output เป็นหลัก ไม่ใช่งานที่ใช้ซีพียูหนัก

โมเดล event loop ของ Node.js รองรับการเชื่อมต่อพร้อมกันจำนวนมากได้ดีอยู่แล้ว
เพราะเวลาส่วนใหญ่หมดไปกับการรอข้อมูลจากซ็อกเก็ต ไม่ใช่การคำนวณ

การเพิ่ม worker thread จะทำให้ต้องจัดการการแบ่งปันสถานะระหว่างเธรด ซึ่งเพิ่มความซับซ้อน
และเพิ่มโอกาสเกิด race condition โดยไม่ได้ประสิทธิภาพเพิ่มขึ้นจริง

สิ่งที่สำคัญกว่าคือ **ทุกการเชื่อมต่อต้องมีบัฟเฟอร์และตัวถอดรหัสเป็นของตัวเอง**
ถ้าใช้ตัวถอดรหัสร่วมกันระหว่างสองการเชื่อมต่อ ไบต์ของสองสตรีมจะปนกันและเสียหายทั้งคู่
ข้อนี้สำคัญกว่าเรื่องเธรดมาก และเป็นสิ่งที่ผมทดสอบไว้ในกรณีไคลเอนต์สองรายทำงานพร้อมกัน"

## กลุ่มที่ 4 — สถาปัตยกรรมและข้อจำกัดของโครงงาน

### ถาม 4.1 ⭐ ตัวเชื่อมใช้ HTTP ถือว่าผิดเงื่อนไขของโครงงานหรือไม่

**แนวคำตอบ** — ต้องตอบให้ชัดเจนและมั่นใจ

"ไม่ผิดครับ และผมออกแบบให้ชัดเจนว่าทำไม

เหตุผลที่ต้องมีตัวเชื่อมคือ **เบราว์เซอร์เปิดซ็อกเก็ต TCP ดิบไม่ได้** เป็นข้อจำกัดด้านความปลอดภัย
ของตัวเบราว์เซอร์เอง ไม่มีทางเลี่ยง ถ้าต้องการให้มีส่วนติดต่อกราฟิก ต้องมีกระบวนการบนเครื่อง
ถือซ็อกเก็ตแทน

แต่จุดสำคัญมีสามข้อ

ข้อแรก ตัวเชื่อม **ไม่เคยส่ง SLTP ผ่าน HTTP** มันรับคำสั่ง _เกี่ยวกับ_ SLTP จากหน้าเว็บ
แล้วสร้างข้อความ SLTP ขึ้นมาส่งบน TCP ดิบอีกทอดหนึ่ง กรอบของ SLTP ไม่เคยวิ่งผ่าน HTTP เลย

ข้อสอง **ไคลเอนต์บรรทัดคำสั่งซึ่งเป็นไคลเอนต์หลักไม่ผ่านตัวเชื่อมเลย** มันเชื่อมต่อ TCP โดยตรง
และใช้งานได้ครบทุกความสามารถโดยไม่ต้องมีตัวเชื่อมหรือหน้าเว็บอยู่เลย ทุกอย่างที่ผมสาธิตวันนี้
ทำผ่าน CLI ทั้งหมด

ข้อสาม HTTP อยู่ระหว่างหน้าเว็บกับกระบวนการบนเครื่องเดียวกันบน loopback เท่านั้น
ไม่ใช่โปรโตคอลระหว่างไคลเอนต์กับเซิร์ฟเวอร์

เงื่อนไขของโครงงานอนุญาตให้ใช้เซิร์ฟเวอร์ HTTP ภายในเครื่องเพื่อให้บริการหน้าเว็บได้
ตราบใดที่มันไม่แทนที่ SLTP ซึ่งกรณีนี้ไม่แทนที่ครับ"

### ถาม 4.2 ทำไมไม่ใช้ WebSocket ในตัวเชื่อม จะง่ายกว่า

**แนวคำตอบ**

"สองเหตุผลครับ

เหตุผลแรก WebSocket อยู่ในรายการเทคโนโลยีต้องห้ามของโครงงานนี้ ผมจึงไม่ใช้

เหตุผลที่สอง ในทางเทคนิคผมไม่ต้องการมันจริง ๆ ช่องทางที่ผมต้องการคือการส่งเหตุการณ์
ทางเดียวจากตัวเชื่อมไปยังหน้าเว็บ ซึ่ง Server-Sent Events ทำได้พอดี
เป็น HTTP ธรรมดาที่ใช้ชนิดเนื้อหา `text/event-stream` ไม่ต้องพึ่งไลบรารีภายนอกเลย

WebSocket มีประโยชน์เมื่อต้องการสื่อสารสองทางแบบเต็มรูปแบบ แต่คำสั่งจากหน้าเว็บ
ไปยังตัวเชื่อมเป็นคำขอกับคำตอบธรรมดาอยู่แล้ว จึงใช้ HTTP ปกติได้

ผมยังทำให้ตัวเชื่อมส่งเหตุการณ์ย้อนหลังให้ผู้ที่เพิ่งเชื่อมต่อเข้ามาด้วย ดังนั้นถ้ารีเฟรชหน้าเว็บ
ไทม์ไลน์จะไม่หายไป"

### ถาม 4.3 ทำไมข้อมูลถึงเก็บแค่ในหน่วยความจำ ไม่เก็บลงฐานข้อมูล

**แนวคำตอบ**

"เป็นการตัดสินใจโดยเจตนาสำหรับรุ่น 0.1 ครับ ไม่ใช่สิ่งที่มองข้าม

เหตุผลคือเครื่องมือนี้ตอบคำถามว่า 'โปรโตคอลของฉันรับมือการแบ่งข้อความได้หรือไม่'
ซึ่งเป็นคำถามที่ตอบได้จบภายในการรันครั้งเดียว ไม่จำเป็นต้องเก็บข้ามการรัน

การเพิ่มฐานข้อมูลจะเพิ่มการติดตั้ง เพิ่ม schema migration และเพิ่มความซับซ้อน
โดยไม่ได้ช่วยเรื่องความถูกต้องของโปรโตคอล ซึ่งเป็นจุดที่ผมต้องการทุ่มเวลาให้

ผมมีทางออกระหว่างกลางไว้แล้ว คือคำสั่ง `result export` ที่เขียนผลทั้งหมดออกเป็นไฟล์ JSON
และสถานการณ์ทดสอบก็เก็บเป็นไฟล์ JSON อยู่แล้ว จึงแบ่งปันและรันซ้ำได้

การเก็บข้อมูลถาวรอยู่ในแผนพัฒนาต่อครับ"

### ถาม 4.4 ทำไมไม่มีระบบยืนยันตัวตน ไม่อันตรายหรือ

**แนวคำตอบ**

"อันตรายถ้านำไปเปิดรับการเชื่อมต่อจากเครือข่ายภายนอก ซึ่งผมระบุไว้ชัดเจนในเอกสารว่าห้ามทำ

เครื่องมือนี้ผูกกับ `127.0.0.1` เท่านั้น ใครที่เชื่อมต่อได้ก็คือคนที่รันโปรแกรมอยู่บนเครื่องนั้นแล้ว
ซึ่งมีสิทธิ์ทำอะไรก็ได้บนเครื่องตัวเองอยู่แล้ว การเพิ่มระบบยืนยันตัวตนในบริบทนี้
จะเพิ่มความซับซ้อนโดยไม่เพิ่มความปลอดภัยจริง

แต่ผมไม่ได้ละเลยเรื่องความปลอดภัยทั้งหมด สิ่งที่ทำไว้คือ
จำกัดขนาดข้อความสี่ระดับเพื่อป้องกันการใช้หน่วยความจำจนหมด
จำกัดอัตราคำขอด้วยกลไกถังโทเคนแยกตามการเชื่อมต่อ ตอบ 429 เมื่อเกิน
จำกัดจำนวนการเชื่อมต่อ ตอบ 503 เมื่อถึงขีดจำกัด
ปฏิเสธค่าส่วนหัวที่มี CR หรือ LF อยู่ภายใน เพื่อป้องกันการปลอมโครงสร้างข้อความ
และปฏิเสธสถานการณ์ทดสอบที่เล็งไปยังโฮสต์ที่ไม่ใช่ปลายทางสำหรับการพัฒนา

ข้อสุดท้ายสำคัญ เพราะทำให้มั่นใจว่าเครื่องมือนี้ใช้ทดสอบระบบของผู้ใช้เองเท่านั้น
ไม่สามารถนำไปยิงระบบของคนอื่นได้"

### ถาม 4.5 ทำไมแต่ละเซสชันต้องเปิดพอร์ต TCP จริง ไม่จำลองในหน่วยความจำ

**แนวคำตอบ**

"เพราะถ้าจำลองในหน่วยความจำ ผมจะพิสูจน์อะไรไม่ได้เลยครับ

ถ้าผมสร้างการแบ่งข้อความขึ้นในหน่วยความจำ มันเป็นแค่การเรียกฟังก์ชันของผมเองเจ็ดครั้ง
ซึ่งไม่ได้บอกอะไรเกี่ยวกับพฤติกรรมของ TCP จริง ๆ เลย

แต่เมื่อเปิดพอร์ตจริง การเรียก `write()` เจ็ดครั้งคือเจ็ดครั้งจริงบนซ็อกเก็ตจริง
ข้อมูลผ่านเคอร์เนล ผ่านสแตก TCP ของระบบปฏิบัติการ และปลายทางก็ต้องประกอบคืน
จากไบต์ที่ทยอยมาถึงจริง ๆ ผลที่เห็นจึงเป็นพฤติกรรมของ TCP จริง

ต้นทุนคือแต่ละเซสชันใช้พอร์ตหนึ่งพอร์ต ซึ่งผมให้ระบบปฏิบัติการจัดสรรให้เพื่อไม่ให้ชนกัน
และปิดคืนเมื่อปิดเซสชัน ซึ่งเป็นต้นทุนที่คุ้มค่ามากเมื่อเทียบกับความน่าเชื่อถือของผลลัพธ์"

## กลุ่มที่ 5 — การทดสอบและคุณภาพของโค้ด

จุดที่น่าสนใจคือ **ถ้าตัวอย่างที่ 4 กลับมาผ่านขึ้นมาเมื่อไร ตัวรันจะรายงานว่าล้มเหลว**
เพราะนั่นแปลว่าตัวตรวจสอบผลคาดหวังพังไปแล้ว การทดสอบที่ควรจับความผิดได้แต่กลับไม่จับ
คือบั๊กที่อันตรายกว่ามาก"

### ถาม 5.3 ทำอย่างไรให้เอกสารกับโค้ดไม่ขัดแย้งกัน

คำสั่ง `npm run examples` จะเปิดเซิร์ฟเวอร์ของตัวเองบนพอร์ตที่ระบบจัดสรรให้ รันทุกสถานการณ์
ในทั้ง 11 ตัวอย่าง แล้วเทียบผลกับสิ่งที่ README ของแต่ละตัวอย่างอ้างไว้
ถ้าไม่ตรงกันเมื่อใด สคริปต์จะจบด้วยรหัสข้อผิดพลาดทันที

นอกจากนี้ ทะเบียนรหัสสถานะและทะเบียนปฏิบัติการอยู่ในไฟล์ซอร์สเพียงที่เดียว
เอกสารอ้างอิงจากที่นั่น ไม่ได้คัดลอกไปเก็บไว้ซ้ำ

ผลคือถ้าผมเปลี่ยนพฤติกรรมของโปรโตคอลแล้วลืมอัปเดตเอกสาร ระบบตรวจสอบจะฟ้องทันที
เอกสารจึงไม่มีทางล้าสมัยแบบเงียบ ๆ"

### ถาม 5.4 ทำไมต้องแยกเป็นหกแพ็กเกจ ไม่ซับซ้อนเกินไปหรือ

`packages/protocol` แยกเพราะมันต้องไม่แตะ API ของ Node.js เลย จึงจะให้เบราว์เซอร์นำเข้าไปใช้ได้
ข้อจำกัดนี้บังคับให้ตรรกะของโปรโตคอลบริสุทธิ์ และเป็นเหตุผลที่หน้าเว็บกับ CLI
ใช้ตัวแจงชุดเดียวกันโดยไม่ต้องเขียนซ้ำ

`packages/core` แยกเพราะทั้งเซิร์ฟเวอร์ CLI และตัวเชื่อมใช้ตรรกะโดเมนชุดเดียวกัน

สามส่วนที่เหลือคือแอปพลิเคชันสามตัวที่โจทย์กำหนดไว้ บวกตัวเชื่อมที่จำเป็นเพราะเบราว์เซอร์
เปิดซ็อกเก็ตไม่ได้

ผมระวังเรื่องการแบ่งชั้นมากเกินไปครับ จึงไม่มีชั้น repository ชั้น service หรือ dependency injection
container ที่ไม่จำเป็น การแบ่งทั้งหมดมาจากขอบเขตที่มีอยู่จริง ไม่ใช่จากรูปแบบที่ตั้งไว้ล่วงหน้า"

## กลุ่มที่ 6 — คำถามเชิงลึกและคำถามที่ตอบยาก

### ถาม 6.1 ถ้าต้องรองรับข้อความขนาดใหญ่กว่า 1 MiB จะทำอย่างไร

**แนวคำตอบ**

"ปัญหาไม่ได้อยู่ที่ตัวเลข 1 MiB ครับ แต่อยู่ที่สถาปัตยกรรมที่สะสมทั้งข้อความไว้ในหน่วยความจำก่อนประมวลผล

ถ้าจะรองรับข้อความขนาดใหญ่จริง ๆ ผมต้องเปลี่ยนเป็นการประมวลผลแบบสตรีม
คือส่งมอบเนื้อความเป็นชิ้น ๆ ให้ผู้ใช้แทนที่จะรอครบก่อน ซึ่งเปลี่ยนอินเทอร์เฟซของตัวถอดรหัส
จาก 'ส่งออกข้อความสมบูรณ์' เป็น 'ส่งออกส่วนหัวก่อน แล้วตามด้วยสตรีมของเนื้อความ'

ทางเลือกอีกทางคือเพิ่มการกำหนดขอบเขตแบบเป็นก้อน คล้าย chunked encoding
ซึ่งจะทำให้ส่งข้อมูลที่ไม่ทราบความยาวล่วงหน้าได้

สำหรับรุ่น 0.1 ที่เน้นข้อความควบคุมและ payload ทดสอบ 1 MiB เกินพอครับ
และการมีขีดจำกัดที่บังคับใช้จริงดีกว่าการไม่มีขีดจำกัดแล้วให้หน่วยความจำหมดโดยไม่รู้ตัว"

### ถาม 6.2 ถ้าออกแบบใหม่ จะเปลี่ยนอะไร

**แนวคำตอบ** — คำถามนี้วัดว่าประเมินงานตัวเองได้หรือไม่ ควรตอบอย่างจริงใจ

"มีสามข้อครับ

ข้อแรก ผมจะเพิ่มการทดสอบคอมโพเนนต์ของส่วนติดต่อกราฟิกตั้งแต่ต้น ตอนนี้ตรรกะสำคัญ
อยู่ในแพ็กเกจที่ทดสอบแล้ว แต่ตัวคอมโพเนนต์ยังไม่มีชุดทดสอบ ซึ่งเป็นช่องว่างที่ผมยอมรับ

ข้อสอง ผมจะพิจารณาให้ส่วนหัวรองรับค่าหลายค่าอย่างเป็นทางการตั้งแต่แรก
ตอนนี้ส่วนหัวสำคัญเป็นค่าเดียวทั้งหมด ซึ่งเพียงพอสำหรับตอนนี้ แต่ถ้าต้องขยายในอนาคต
การเปลี่ยนทีหลังจะยากกว่าการออกแบบไว้ตั้งแต่ต้น

ข้อสาม ผมจะสร้างเอกสารรหัสสถานะจากทะเบียนในโค้ดโดยอัตโนมัติตั้งแต่แรก
แทนที่จะเขียนแล้วค่อยมาตรวจว่าตรงกันภายหลัง

สิ่งที่จะไม่เปลี่ยนเลยคือการตัดสินใจให้ปลายทางจำลองเป็นพอร์ต TCP จริง
และการแยก `packages/protocol` ไม่ให้แตะ API ของ Node.js สองข้อนี้เป็นการตัดสินใจที่ถูกต้อง"

### ถาม 6.3 เครื่องมือนี้ต่างจาก Wireshark หรือ Postman อย่างไร

**แนวคำตอบ**

"ต่างกันที่บทบาทครับ

Wireshark เป็นเครื่องมือสังเกตการณ์ มันดูสิ่งที่เกิดขึ้นแล้ว แต่ทำให้เกิดเหตุการณ์ไม่ได้
ถ้าผมอยากรู้ว่าโปรแกรมรับมือกับข้อความที่แบ่งเป็นเจ็ดส่วนได้ไหม Wireshark บอกไม่ได้
จนกว่ามันจะเกิดขึ้นเองซึ่งอาจไม่เกิดเลยบนเครื่องทดสอบ

SocketLens TCP **สร้าง** สถานการณ์นั้นขึ้นมาตามที่กำหนด และตรวจสอบผลให้ด้วย

ส่วน Postman ทำงานบน HTTP ซึ่งมีการกำหนดขอบเขตข้อความมาให้แล้วในตัว
มันไม่ให้ผมควบคุมว่าข้อความจะถูกแบ่งเป็นกี่ส่วนที่ตำแหน่งไหน เพราะนั่นไม่ใช่ปัญหาของ HTTP
แต่มันเป็นปัญหาหลักของคนที่ออกแบบโปรโตคอลบน TCP เอง

สรุปคือ Wireshark ตอบว่าเกิดอะไรขึ้น Postman ตอบว่า HTTP API ทำงานถูกไหม
ส่วนเครื่องมือของผมตอบว่าตัวถอดรหัสของคุณรับมือกับสิ่งที่ TCP ทำได้จริงหรือไม่"

### ถาม 6.4 ถ้ามีคนอยากใช้โปรโตคอลของตัวเองไม่ใช่ SLTP จะทำได้ไหม

**แนวคำตอบ**

"ตอนนี้ยังไม่ได้เต็มรูปแบบครับ แต่มีทางออกบางส่วนอยู่แล้ว

สถานการณ์ทดสอบรองรับการส่งไบต์ดิบผ่านฟิลด์ `raw` ดังนั้นผู้ใช้ส่งอะไรก็ได้ขึ้นสายจริง ๆ
รวมถึงข้อความของโปรโตคอลตัวเอง และดูได้ว่าปลายทางตอบอะไรกลับมา

สิ่งที่ยังไม่มีคือการให้ระบบเข้าใจและแจงโปรโตคอลของผู้ใช้ ตอนนี้ตัวแจงยังผูกกับ SLTP อยู่

การทำให้รองรับได้ต้องแยกกฎการกำหนดขอบเขตออกมาเป็นส่วนที่เสียบเปลี่ยนได้ ซึ่งเป็นไปได้
เพราะตัวถอดรหัสของผมแยกเรื่องการกำหนดขอบเขตออกจากเรื่องความหมายอยู่แล้วในระดับหนึ่ง
ผมระบุเรื่องนี้ไว้เป็นแนวทางพัฒนาต่อในชื่อปลั๊กอินไวยากรณ์โปรโตคอลครับ"

### ถาม 6.5 ใช้เวลาทำนานเท่าไร และส่วนไหนยากที่สุด

**แนวคำตอบ**

"ส่วนที่ยากที่สุดไม่ใช่การเขียนตัวถอดรหัสครับ แต่เป็นการ **ทำให้แน่ใจว่ามันถูกจริง**

การเขียนตัวถอดรหัสให้ทำงานได้ในกรณีปกติใช้เวลาไม่นาน แต่การคิดให้ครบว่ามีกรณีขอบอะไรบ้าง
และเขียนการทดสอบให้ครอบคลุมกินเวลามากกว่าหลายเท่า กรณีที่ผมคิดถึงทีหลังและยากที่สุด
คือการแบ่งข้อมูลกลางตัวอักษร UTF-8 แบบสามไบต์ ซึ่งเป็นเหตุผลที่ผมต้องทำงานบน Buffer ตลอด
และแปลงเป็นข้อความเฉพาะตอนที่เนื้อความครบแล้วเท่านั้น

อีกส่วนที่ยากคือการทำให้ตัวอย่างที่ตั้งใจให้ล้มเหลวถูกจัดการอย่างถูกต้อง
เพราะต้องแยกให้ออกระหว่าง 'ล้มเหลวตามที่ตั้งใจ' กับ 'ล้มเหลวเพราะมีบั๊ก' ซึ่งเป็นคนละเรื่องกัน"

## สรุปสามประโยคที่ควรจำให้ขึ้นใจ

1. **TCP เป็นสตรีมไบต์ที่เชื่อถือได้และรักษาลำดับ แต่ไม่รักษาขอบเขตของข้อความระดับแอปพลิเคชัน**
2. **`Content-Length` นับเป็นไบต์ ไม่ใช่อักขระ** เพราะสิ่งที่วิ่งบนสายคือไบต์
3. **เมื่อขอบเขตของข้อความไม่อาจทราบได้ ต้องปิดการเชื่อมต่อ ไม่ใช่เดา** เพราะการเดาผิดทำให้สตรีมเสียหายถาวร
